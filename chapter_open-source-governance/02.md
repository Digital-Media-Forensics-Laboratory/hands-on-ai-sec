# 二、开源许可协议与安全责任界定

[本章目录](index.md) · [全书目录](../index.md) · [上一节](../chapter_open-source-governance/01.md) · [下一节](../chapter_open-source-governance/03.md)

## （一）开源许可协议

开源许可协议是著作权人允许他人使用开源软件时所附加的法律规则。源代码公开并不意味着任何人都可以不受限制地使用，软件的复制、修改和再分发仍然受到著作权保护。开源项目通过许可协议预先授予使用者相应权利，同时规定在修改或重新发布软件时需要履行的义务。因此，许可协议既是开源软件能够广泛传播和协作开发的法律基础，也是项目开发者、贡献者和后续使用者之间划分权利边界的重要工具。按照开放源代码促进会的基本标准，开源许可证应当允许软件被自由使用、修改和共享，但不同许可证可以对再分发和衍生作品提出不同要求。

不同开源许可协议最主要的差异，在于开放权利之后是否要求后续开发成果继续保持相同或类似的开放状态。根据这种差异，常见许可协议大体可以分为宽松型许可证和Copyleft[[175]](../chapter_references/index.md#ref-175)许可证。宽松型许可证通常只要求保留版权声明和许可文本，对修改后的代码采用何种许可证限制较少。Copyleft许可证则在允许自由使用和修改的同时，通常在再分发时，要求部分或全部受覆盖的衍生作品继续按规定提供源代码。不同协议对这一要求的范围又有所区别，由此形成强Copyleft、弱Copyleft以及文件级Copyleft等不同形式。

MIT许可证[[31]](../chapter_references/index.md#ref-31)是较为典型的宽松型许可证。其条款较为简洁，允许使用者复制、修改和再分发软件，也允许将软件用于商业项目。使用者在重新发布时主要需要保留原有版权声明和许可声明。由于对衍生作品的许可方式限制较少，MIT许可证给予后续开发者较大的再利用空间，但也意味着修改后的成果可以被整合进不开源的软件中。

Apache License 2.0[[34]](../chapter_references/index.md#ref-34)同样属于宽松型许可证，但相比MIT许可证，它对知识产权关系的规定更详细。除要求在再分发时保留许可证和相关声明外，Apache License 2.0明确提供了贡献者所拥有相关专利的许可，并规定在特定专利诉讼情况下终止相应专利授权。对于修改过的文件，使用者还需要作出相应说明。明确的专利授权安排使Apache License 2.0较适合参与主体较多，特别是企业广泛参与的开源项目。

GNU通用公共许可证（GNU General Public License，GPL）[[176]](../chapter_references/index.md#ref-176)代表了较强的Copyleft模式。GPL允许软件被使用和修改，但如果将修改后的程序或者受GPL约束的衍生作品进一步分发，通常需要同时提供相应源代码，并继续按照GPL规定的条件向接收者授予权利。GPL希望通过这种方式避免开放代码在后续传播过程中被转化为完全封闭的软件，使使用者从开源项目中获得的基本自由能够继续传递给后续使用者。GPL第3版还进一步涉及专利授权以及用户修改软件的实际能力等问题。

在GPL基础上还形成了一些适用于不同协作场景的许可证。GNU较宽松通用公共许可证（LGPL）[[177]](../chapter_references/index.md#ref-177)主要用于软件库，其Copyleft要求相对较弱。采用LGPL的软件库可以在满足相应条件的情况下与其他许可证的软件结合使用，但对该库本身进行修改后再分发时，仍需遵守LGPL的开放要求。Mozilla公共许可证2.0（MPL 2.0）[[178]](../chapter_references/index.md#ref-178)则采用文件级的Copyleft机制，要求在对外分发时，为受MPL覆盖的文件及其修改提供遵循MPL的源代码，但允许这些文件与采用其他许可证的代码共同组成更大的软件，因此在开放与商业再利用之间保留了较大的组合空间。

GNU Affero通用公共许可证（AGPL）[[179]](../chapter_references/index.md#ref-179)进一步将Copyleft要求延伸到通过网络提供软件服务的情形。传统GPL的部分义务通常与软件的分发行为相联系，如果软件经过修改后只部署在服务器端而不向用户分发程序副本，相关源代码可能无需因为这一使用方式而公开。AGPL针对这一场景增加了网络交互条款，要求修改后的程序通过网络与用户交互时，为这些用户提供获得相应源代码的机会。这使AGPL尤其关注云服务和网络应用中“使用但不分发”所产生的开放性问题。

不同许可证在衍生作品处理和知识产权安排上各有侧重。宽松型许可证更重视代码流通和再利用自由，Copyleft许可证则更关注开放成果能否在后续传播中继续保持开放。项目选择何种许可证，会直接影响后续贡献者和使用者可以如何利用代码，也决定其在修改、组合和再次传播软件时需要承担哪些义务。几种较有代表性的开源许可协议及其主要规则如表6-3所示。

## （二）安全责任界定

开源许可协议在赋予使用者较大使用自由的同时，通常也会对软件质量担保和损害赔偿责任作出限制。MIT License明确规定软件按照“现状”提供，作者或著作权人原则上不对软件使用产生的损害承担责任；Apache License 2.0同样设置了免责声明和责任限制，并明确由使用者自行判断软件是否适合使用。GPL也规定软件原则上不提供质量担保，并对著作权人和其他参与者的赔偿责任进行限制。这些条款与开源软件的协作方式密切相关。大量项目由不同开发者共同完成，如果要求每一名贡献者都对软件最终运行结果承担完整担保责任，将明显增加参与开源项目的成本。

但许可证中的免责声明并不意味着开源软件处于“无人负责”的状态。一方面，Apache License 2.0和GPL等协议本身都为适用法律另有强制规定的情形保留了空间，因此许可协议不能当然排除法律规定的责任。另一方面，随着开源软件被广泛用于商业产品和重要信息系统，安全责任也逐渐从单纯讨论开发者是否承担担保责任，转向根据不同主体在软件开发、维护和使用过程中的实际控制能力划分责任。

### （1）项目维护者和贡献者主要承担项目内部的安全治理责任

普通贡献者通常只负责自己提交的代码，并不当然对整个项目的安全性承担责任。核心维护者掌握代码审核和版本发布权限，对项目运行具有更强的实际控制能力，因此也承担更多安全治理工作。对于已经发现的漏洞，维护团队需要建立合理的接收和处理渠道，对问题进行确认并组织修复，同时控制漏洞在修复完成前的传播范围。相关平台提供的漏洞报告、安全公告和保护分支等工具，可以为维护者履行这类责任提供技术支持；不同平台具体支持的功能和访问条件有所不同。

### （2）开源社区和平台主要承担规则与处置责任

GitHub、GitLab和Gitee并不直接开发平台上的全部开源项目，因此一般不能等同于具体软件的开发者，也难以对每个项目的技术安全作出保证。但平台控制着代码发布和社区互动所依赖的基础设施，可以制定社区规则并提供举报渠道，在发现恶意项目或违规内容后采取限制访问等措施。对于安全漏洞，平台还可以提供非公开报告和协作修复工具。由此，平台承担的重点并不是替代维护者保证软件没有漏洞，而是建立基本的社区规则和安全处置机制。

### （3）下游使用者和商业集成者需要承担相应的安全审查责任

开源许可证允许软件被自由使用，并不意味着使用者可以将全部安全风险继续转移给原始开发者。企业将开源组件集成到自己的产品中时，需要根据产品用途评估组件是否适合使用，并关注已知漏洞和后续更新。如果对开源代码进行修改并作为自身产品的一部分向用户提供，相关主体对最终产品具有更强的控制能力，也应承担与这种控制能力相匹配的安全责任。特别是在关键系统中使用开源软件时，仅以“代码来自开源社区”为由完全免除使用者自身的安全审查责任并不合理。

近年来的监管规则也开始体现这种分层责任思路。欧盟《网络韧性法案》[[181]](../chapter_references/index.md#ref-181)（Cyber Resilience Act，CRA）并未简单地将所有开源开发者纳入统一的产品责任体系。对于不在商业活动中提供的自由和开源软件，法规给予了特殊处理，普通开发者仅向并非由自己负责的开源项目贡献代码，并不会因此承担制造商责任。与此同时，法规专门引入了“开源软件管理者”（open-source software steward）这一主体，对那些长期、系统性支持面向商业活动的开源项目并保障其持续运行的组织提出安全要求，包括建立网络安全政策并推动漏洞报告与修复，同时要求其在一定条件下与市场监管机构合作。对于将开源软件作为自身产品投入市场的制造商，责任则进一步增强，需要开展网络安全风险评估，并承担产品安全维护等义务。

责任划分应结合参与角色：贡献者关注自身提交内容，维护者承担项目审核与漏洞处理，平台提供规则和处置机制，下游企业评估并管理集成后的风险。这反映出责任体系正从许可证免责讨论，转向兼顾控制能力、参与程度和商业化程度的分层安排。
